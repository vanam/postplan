Choices to approve

  1. Path-based slugs. Use /s/warehouse-plan/ on the existing hostname. A slug resolves to the stable draft route. No wildcard DNS, additional Worker routes, or per-draft subdomains.
  2. Limits for authenticated publishing. Every upload requires a valid API key, whether it contains one page, a folder, or a slug. Allow up to 20 HTML pages per version. Keep the current 512 KiB aggregate limit and configurable request-body limit; larger account tiers and flags are outside this change.
  3. Sandboxed inline scripts. New versions may execute classic inline scripts with a CSP sandbox that does not grant same-origin access, storage, forms, popups, or top navigation. External scripts, modules, event-handler attributes, and network requests remain blocked. Existing versions retain their current script-blocked behavior. A permission change requires a new version even when HTML bytes match.

If you prefer to defer scripts, the rest can ship with capabilities.inlineScripts: false and an explicit warning that interactive content will not execute. That would be partial CLI parity, documented as such.

Data model and publication

  • Build on the existing public-upload removal migration. Preserve surviving account-owned drafts and versions. Do not recreate the removed public account or restore drafts deleted by that migration; cleanup of their leftover R2 objects is outside this feature work.
  • Add an additive migration with a nullable unique slug on drafts and a draft_version_pages table keyed by version and page path. Each row records its R2 object key, byte count, content hash, title, and script metadata.
  • Preserve the existing version row as the upload-level record. Its hash and size represent the entire upload. Keep its existing object key for the index page so old versions need no R2 rewrite.
  • Backfill old versions as one index.html page using existing metadata. Add an explicit per-version script permission defaulting to false so old HTML does not gain execution rights.
  • Normalize single-file uploads to index.html. Folder uploads require that page and accept HTML only, including nested paths. Reject duplicate paths, traversal, absolute paths, encoded separators, ambiguous input containing both html and files, and reserved route names.
  • Hash single-page content as before. Hash multiple pages using a sorted path/content-hash manifest. Input ordering must not affect the result.
  • Validate the entire upload before writing. Put each page in R2, then commit the version, page manifest, draft pointer, slug changes, and audit event in one D1 batch. Clean up newly written objects if R2 or D1 fails; never delete objects belonging to an existing version.
  • Use database uniqueness and conditional updates to handle concurrent slug claims, version allocation, and identical uploads. A race must not create two owners for a slug or move the current pointer backwards.

Keep existing single-page /d/<id>, /raw, and numbered-version URLs working. Return a trailing-slash index URL for new multi-page uploads so relative links resolve correctly. Historical links stay within their selected version. Missing pages return 404; they never fall back to the index. HTML bytes remain unchanged.

Raw routes return the same HTML bytes with the same security restrictions. Their purpose is retrieval; normal page URLs are used for browsing linked pages. Reserve top-level raw and v paths to prevent route collisions. Root-relative links are diagnosed because they address the service root rather than the draft's folder.

Slug behavior

  • Use a lowercase slug of 1 to 63 letters, digits, and internal hyphens, starting and ending with a letter or digit. Reject invalid input rather than silently truncating it.
  • An unused slug creates a draft. Reusing your own slug updates it. A slug owned by another account returns 409. --draft <id> --slug <name> renames an owned draft; the previous slug becomes available.
  • Ownership is checked through the authenticated account, never through knowledge of a URL. Deleted drafts release their slug; disabled drafts reserve theirs and do not serve content.
  • Slug availability in check is advisory. Upload rechecks it atomically. Receipts keep the stable draft ID in update commands so later slug reuse cannot retarget an update.

Check and receipt contracts

POST /api/check requires a valid API key and accepts an optional single page or page collection and an optional slug. With no file, it reports readiness only. It returns the fields the current CLI reads: ok, account, flags, limits, capabilities, slug, pages, totalBytes, issues, errors, and warnings. The account is always populated in a successful authenticated report.

A validation failure produces a complete report with ok: false. Missing, invalid, or revoked credentials return 401 before validation. Malformed input, oversized bodies, and rate limiting retain proper HTTP error statuses. Check never writes draft metadata or HTML objects and never consumes upload quota. Reuse bounded validation and a separate check rate limit; normal authentication bookkeeping may still occur.

Upload responses add created, unchanged, slug, versionUrl, contentHash, totalBytes, account, and pages, while retaining existing response fields. /api/me returns an explicit empty flags array until account flags exist.

Identical content with the same execution permission returns the current version without another R2 write or version allocation. Requested description or slug changes still apply and receive an audit event. Changed content or execution permission creates a version. Uploads continue to return 401 for missing, invalid, or revoked API keys. Every receipt names the owning account.

Shared validation and script isolation

Extract markup validation and issue formatting into a small shared workspace consumed by both server and CLI. Keep hashing in runtime adapters, using Worker Web Crypto and Node crypto as appropriate. The npm tarball must remain standalone, with no unresolved workspace dependencies.

Preserve the Worker's existing restrictions unless a rule is deliberately approved here. Add page paths and source positions to diagnostics; distinguish executable scripts from inert JSON data blocks. Offline checking can validate markup, but must not claim to know account permissions, slug ownership, or server limits.

Keep offline markup checking useful without credentials: when no key is configured, the CLI checks markup locally and returns ok: false, offline: true, and an authentication-required explanation. It never calls that result ready to publish. With a key, it calls the authenticated check endpoint; an unreachable server uses the same local fallback. A 401 is an authentication error, not a network failure. Update both JSON and human output so neither suggests anonymous publishing or a higher anonymous/account tier.

If scripts are approved, serving selects CSP from the stored version permission. Authenticate before granting that permission. Test the real browser behavior for origin isolation and blocked operations, including the raw route. This is required before calling interactive uploads complete; upload validation alone cannot prove browser isolation.

Implementation order

  1. Define payload, receipt, check, page-path, slug, and permission contracts. Add the shared validator and focused policy tests.
  2. Add and test the D1 migration against existing single-page data. Implement page manifests, deterministic hashing, atomic version commits, unchanged uploads, and failure cleanup.
  3. Add page serving and slug resolution. Verify old URLs, relative navigation, historical pages, deletion, disabling, and ownership.
  4. Add authenticated readiness checks, capability reporting, full receipts, and CLI adjustments for missing credentials, path-based URLs, and accurate offline reporting.
  5. If approved, add authenticated script permission and CSP sandboxing. Verify isolation in a local browser preview.
  6. Update API documentation, CLI examples, and relevant bundled skill guidance. Build the standalone npm tarball and verify commands against a disposable local Worker.

Acceptance checks

  • The existing server and CLI suites pass. A surviving account-owned draft migration fixture still serves its exact original bytes and historical versions. The removed public-upload account stays absent.
  • A real CLI folder upload serves index and nested pages; links and version URLs resolve to the expected content. Traversal and conflicting reserved paths are rejected.
  • Slug creation, reuse, rename, ownership conflicts, and concurrent claims behave as specified.
  • Identical uploads report unchanged and do not allocate extra versions or objects. Concurrent changed uploads preserve unique version numbers and a valid current manifest.
  • Failed page writes and failed D1 commits clean up only newly created objects.
  • check --json and human output work for authenticated users, invalid HTML, oversized folders, and unavailable slugs without publishing. Missing credentials produce a clear local report that does not claim readiness. Direct upload and check requests without a valid key return 401 and create no drafts or R2 objects.
  • Offline markup checks agree with online markup checks, while clearly leaving account limits and slug availability unverified. Invalid and revoked keys are never treated as anonymous identities.
  • Receipts contain every field consumed by the CLI. The packed npx executable works outside the monorepo.
  • If scripts are enabled, browser checks show authenticated interactivity works while forbidden origin, storage, network, form, and navigation operations remain blocked.

Scope boundaries

This is API, persistence, serving, and CLI compatibility work. No dashboard redesign, asset bundling, arbitrary file hosting, wildcard hosting, account billing tiers, or automatic npm publication. Any later non-trivial UI change gets separate static mocks for review.

Implementation uses isolated local D1 and R2 state. Deployment, remote migrations, live database changes, and npm publication remain separate actions requiring explicit instructions. Your decision on this plan comes first.
